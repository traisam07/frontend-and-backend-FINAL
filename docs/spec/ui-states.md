# PulseMind — UI State Matrix

The complete, enumerated list of UI states for the three PulseMind screens. Every state has a stable
ID, the screens it appears on, what must be shown, what must not be shown, and where the requirement
comes from.

**This file is the audit target.** `.claude/skills/ui-state-matrix/SKILL.md` and
`.claude/agents/ui-state-auditor.md` audit implementation against these rows. Treat the IDs as a
public contract.

## Stability contract

- **IDs are permanent.** Never renumber. Never reuse a retired ID.
- To retire a state, keep the row and set its Source column to `RETIRED — <date> — <reason>`.
- To add a state, append the next free ID in the correct block. Blocks:
  - `S-01`…`S-99` — screen and domain states reachable on the handoff's three screens. Most are
    handoff-sourced, but the block is not a provenance claim: read the Source column per row.
  - `U-01`…`U-99` — production states the handoff's three screens do not cover. A row sourced
    `UNDEFINED-NEEDS-DECISION` (Handoff section 8) must also have a row in
    `docs/spec/open-questions.md`; a row sourced `HARNESS` (a failure mode of a boundary this
    harness introduced, such as `U-20` and `U-21`) must instead be labelled in the UI.
- Every `[HARNESS]` state must be visibly labelled in the running UI ("harness-defined, pending
  design confirmation") and, where it blocks a safe render, carry a `data-clarify` attribute whose
  value is the **register row ID** it escalates to — `data-clarify="G-04"`, `data-clarify="G-09"`,
  `data-clarify="G-16"` — so a build script can enumerate reachable clarifications. The value is
  always a real `G-*` / `D-*` / `P-*` ID from `docs/spec/open-questions.md`, never a slug
  (`model-use`, `review-null`, `explanation-null` are all wrong): `P-09`'s CI gate fails any id with
  no row in the register.

## Source column vocabulary

| Value | Meaning |
|---|---|
| `HANDOFF section N` | Stated in the handoff PDF. Not negotiable, not re-designable. |
| `SCHEMA` | Implied by `docs/patientSchema.js`. |
| `HARNESS` | Invented by this harness. Harness-defined, pending design confirmation. |
| `UNDEFINED-NEEDS-DECISION` | Handoff section 8 gap. Interim behavior is provisional; the linked open question stays open. |

**Mixed rows must say so.** Most rows are part handoff, part harness. When they are, the Source cell
names both halves explicitly — for example `` `HANDOFF section 6`; the non-colour channel is `HARNESS` ``.
Never let a harness invention sit inside a `HANDOFF`-only cell: that cell grants immunity from design
review, and a reviewer will cite a handoff section that does not say it.

## Screen abbreviations

`OV` = Patient Overview. `PD` = Patient Detail. `PM` = Parameter Detail. Section IDs (`OV-4`,
`PD-10`, `PM-5`, …) are defined in `docs/spec/screens.md`.

## 2. Undefined production states (Handoff section 8)

Handoff section 8 lists these as **not defined by the prototype** and instructs that they must not be
invented. `U-01`…`U-19` and `U-22` are `UNDEFINED-NEEDS-DECISION` and each has a matching row in
`docs/spec/open-questions.md` — `U-22` shares `U-11`'s row, **G-25**, because it shares its cause.
The "MUST show" column is the **interim** `HARNESS` behavior — it exists only so the app is never
undefined at runtime. It does not close the gap.

`U-20` and `U-21` are different and their Source cells say so: the handoff never mentions them,
because they are failure modes of boundaries **this harness introduced** (URL query parameters, and
the validation layer at the API boundary). They are `HARNESS` states, not handoff section 8 gaps —
label them "harness-defined, pending design confirmation" like any other harness state. Read the
Source cell row by row rather than reading the block heading as a provenance claim; the two
`HARNESS` rows sit inside a numeric range that is otherwise `UNDEFINED-NEEDS-DECISION`.

## 3. State interaction rules

These constrain how states combine. They exist because the dangerous defects in this UI are
combinations, not single states.

| # | Rule |
|---|---|
| 1 | S-10 (insufficient data) **gates** PD-8 and PD-9 before any null check. Check `sufficient_data === 'insufficient'` first; only then consider whether `explanation` / `citations` happen to be non-null. |
| 2 | S-19, U-04, U-05, U-06, and U-09 must be **five visibly distinct** treatments. An empty board that could mean any of them is a triage hazard. |
| 3 | U-01 (loading) and U-09/S-19 (empty) must never look alike. |
| 4 | S-13 and S-14 never share a treatment, and neither shares a treatment with S-12. |
| 5 | S-09 ranks above S-07/S-08 (K1 = 1) but is **excluded** from the S-21 `Needs review` filter. The difference is deliberate; do not "fix" either half. |
| 6 | `S-39` (marked on this screen) survives **navigation** — board → detail → board — because the marks are held by `patients/+layout.svelte`, not by either page. Each page builds its own `TriageBoard`, so a mark held there is destroyed on every navigation, and the review history is what made that visible. The marks are keyed by `patient_id`, never by index, and a reload clears them because nothing is persisted (**G-08**). |
| 7 | S-25 (drawer open) survives S-33 and U-03 without closing or moving focus (U-16). |
| 8 | Any state whose data is missing resolves to an explicit unavailable treatment, never to a `disabled` control. `disabled` means "this action is unavailable in this UI state", never "this data is missing". |
| 9 | Every failure path terminates in a named, visible state from this matrix. No `catch` block may resolve to an empty state. |
| 10 | U-14 (stale) composes with every other state: the "as of `<time>` (`<age>`)" stamp is always present wherever clinical values render. |
| 11 | Every field `docs/spec/data-contract.md` section 1.4 leaves nullable **after** validation resolves to a named row here: `charttime` → `U-11` (and `U-22` in the OV-4 card's time slot), `sufficient_data` → `S-10`, `risk_score` → `S-35`, `risk_level` → `S-05` (and `S-38`'s unavailable rendering in PD-6's run-length slot), `ParameterReading.source` → `S-15`. A nullable field with no row is the section 5 step 6 finding — the compiler forces the branch, so the matrix must name it. One nullable field may resolve to more than one row: the rows are per **slot**, not per field. |
| 12 | The explanation/reference slot has **four** treatments that never share a component or a heading: present (S-11), withheld because data is insufficient (S-10), withheld because sufficiency is unknown (S-10's `null` branch), and not supplied although data is sufficient (S-37). The first three are clinical statements about the reading; the fourth is a system statement about the payload (**G-16**). |
| 13 | Every row whose copy is load-bearing carries a **positive mandated literal** in its MUST-show column, not only a MUST-NOT list. A row with bans and no literal delegates the wording to whoever writes the component, which is how one state acquires a second spelling (`docs/LESSONS.md` L-044, L-046, L-047). Adding a state means adding its literal in the same change. |
| 14 | **One literal per slot, and a row may carry several only when it names the discriminant that picks between them.** A row like `S-10` (`insufficient` vs `null`), `U-13` (unknown slug vs unknown patient) or `S-38` (truncated / exact / unavailable) is one slot with a stated branch, which is fine. What is *not* fine is two surfaces saying different things about the same cause inside one row: that is two states. `U-11` and `U-22` share one cause — this patient has no reading with a usable `charttime` — and are two rows, because PD-2 and the `NO_CURRENT_READING` path say the whole assessment is unavailable while the OV-4 card's time slot says only that the assessment *time* is. Neither literal is a retired form of the other, neither may be rendered in the other's slot, and the two rows must not be re-merged (`docs/LESSONS.md` L-049). |

## 4. Banned copy in any unavailable, unknown, or empty state

**This section is the single governing banned-copy list for the product, and it is the superset.** No
other file may hold a competing list. `.claude/skills/clinical-a11y/SKILL.md` section 8.7 and
`.claude/skills/tailwind-design-system/SKILL.md` section 5.9 point here; either may add, at most, an
**explicitly labelled skill-local addition** ("skill-local addition to `ui-states.md` section 4"),
and a term that appears in a skill but not below is a bug in this section — fold it in rather than
letting two lists drift.

Applies to S-05, S-08, S-09, S-15, S-19, S-26, S-29, S-35, S-36, S-37, S-38, S-39, S-40, S-41, and every `U-*`
row.

- "No issues", "No problems found", "All clear", "Nothing to report", "Normal", "Abnormal", "OK",
  "Looks good", "Healthy", "Fine", "Safe"
- "stable", "improving", "worsening", "trend", "trajectory"
- "now", "just now", "moments ago", "recently", "a while ago"
- "live", unless the connection is actually verified — no connection status exists (**G-05**, S-36)
- "confirmed", for anything that has not been persisted
- A bare em dash, a blank cell, an empty region, a collapsed accordion, or a skeleton that never
  resolves, standing in for a missing value
- "Saved" or "Persisted" for the review action while **G-08** is open

Every one of these either asserts a clinical fact the data does not support, or renders an absence as
a reassuring presence.

**A prohibition alone is not a specification.** Every state named above whose copy is load-bearing
also carries a **positive mandated literal** in its own row (section 3 rule 13) — the bans below
constrain the string from one side only, and the set of unbanned wordings is infinite, so a row with
bans and no literal hands the decision to whoever writes the component (`docs/LESSONS.md` L-044,
L-047). Where a row still lists only bans (`U-01`, `U-02`, `U-05`, `U-07`, `U-08`, `U-10`, `U-12`,
`U-15`…`U-19`, whose copy is a whole treatment rather than one string), it is unfinished rather than
compliant:
adding its literal is the next edit to this file, not a later one.

**Retired spellings — one slot, one string.** These lost to a mandated literal and must never
reappear in a document, a component, or a test. A slot with two spellings is a slot a test cannot
assert, and a mandated literal that carries a hedge — "punctuation aside", "or equivalent",
"approximately" — is not mandated (`docs/LESSONS.md` L-046).

**A different state's literal is not a retired spelling.** This table retires wordings *within* one
state's slot. Two states that share a cause but say different things — `U-11` and `U-22`, section 3
rule 14 — each keep their own row here, and neither string may ever be listed as the other's retired
form; doing exactly that is what made two files call each other's mandated copy banned
(`docs/LESSONS.md` L-049).

| Retired | Mandated literal | Declared in |
|---|---|---|
| `Recorded in this session`; `locally marked, not persisted`; `Reviewed · recorded in this session at <time>` | `Marked locally in this session — not saved to the record` | `docs/spec/screens.md` section 8 RULE TWO |
| `Reviewed · time not recorded` | `Reviewed · review time not recorded` | S-08 above |
| `data sufficiency unavailable`; `unknown data` | `data sufficiency unknown`, plus the two headings S-10 mandates | S-10 above |
| `No readings available`; `No data for this patient`; any trailing period on the literal | `No assessment available for this patient` (PD-2 and the `NO_CURRENT_READING` path) | U-11 above |
| `Assessment time unknown`; `No timestamp`; any dropped sentence-final period | `No reading with a usable timestamp. The assessment time is unavailable.` (the OV-4 card's time slot) | U-22 above |
| `>= N readings at this level` (the ASCII form); `Held at this level for N readings` | `≥ N readings at this level`, `N readings at this level`, and `Readings held at this level: unavailable. The latest reading has no risk level.` | S-38 above |
| `Source status unavailable` (bare — it reads as "the devices are DOWN", which is a clinical claim the data cannot support); `Source status unavailable — not provided by the data contract` (**retired 2026-08-17**: the head was ambiguous and the tail was spec vocabulary aimed at the handoff team, which the product owner asked off the screen); `No sources`; `0 sources connected`; `Sources unavailable` | `Device and source status is not reported` — it names what is absent (a REPORT), not a device state, so it cannot be read as an outage | S-36 above |

## 5. How to audit an implementation against this matrix

1. For each row, locate the component that renders the state. If none exists, the state is missing.
2. Confirm the MUST-show column is satisfied in the rendered output, not merely in the code path.
3. Confirm every MUST-NOT-show item is absent — including under refresh, deep link, and error.
4. Confirm the Source column: a row marked `HARNESS` or `UNDEFINED-NEEDS-DECISION` must be visibly
   labelled in the UI and must carry a `data-clarify` id — a literal `G-*` / `D-*` / `P-*` register
   ID, not a slug — that resolves to a row in `docs/spec/open-questions.md`.
5. Confirm the section 3 interaction rules hold, especially rules 1, 2, 5, 6, and 9.
6. Report any state reachable in the app that has **no row here**. That is the highest-severity
   finding: it means a behavior was invented rather than specified.
