# PulseMind — Open Questions Register

The live register of everything the handoff leaves undefined, every gap between the handoff document
and `docs/patientSchema.js`, and every visual or platform decision this harness made in the absence
of a prototype.

Every row now carries two different things and they must not be confused. **Interim behavior** is what
the app does today while nobody has answered — deliberately conservative, often a refusal to render.
**Recommendation `[PROPOSED]`** is the answer we propose the owner adopt, written so the owner can
reply "approved" and we implement it unchanged. A recommendation is an escalation with a proposal
attached, never a decision: every row's Status stays exactly as it is until the named owner answers.

## The standing rule (Handoff section 8)

> **Recommended handling of undefined states.** Where a required production state is missing from the
> prototype, mark it for design/product clarification rather than silently choosing a behavior.

Operationally, for everyone working in this repo:

1. **Add a row here rather than inventing behavior.** If you find yourself picking a default for a
   clinical value, a state, a threshold, a unit, or a colour with nothing in the handoff or the schema
   to back it, stop and open a row.
2. **Surface every new row to the user.** A row added silently is the same failure as a behavior
   invented silently. When you add a row, say so in your response.
3. **Interim behavior is provisional, never a decision.** Every interim must be visible in the UI as
   "harness-defined, pending design confirmation" or as an explicit unknown/unavailable treatment,
   and must carry a `data-clarify="<id>"` attribute so a build script can enumerate every reachable
   open question in the running app.
4. **Never let an interim quietly become permanent.** A row leaves this file only when the owner
   answers it, and the answer lands in the same change in every file that row's `Lands in` clause
   names — usually `docs/spec/data-contract.md`, `docs/spec/ui-states.md` or `docs/spec/screens.md`,
   and for many `D-*` and `P-*` rows a skill under `.claude/skills/`, `CLAUDE.md`,
   `.claude/settings.json`, or a build/config file instead. A row whose answer edits nothing anywhere
   is a row that was never really answered.
5. **Silently choosing a behavior in this product is a patient-safety-class bug**, not a style
   choice.

### How to use the recommendations

1. **A recommendation is an escalation with a proposal attached, never a decision.** It exists so the
   owner has something concrete to approve or reject instead of an open-ended question. It does not
   convert an open question into a settled one, and it never changes the Status column.
2. **Approving one is the owner's act, and it is one act.** The owner replies, the answer lands in
   every file that row's `Lands in` clause names, in the same change, and only then does the Status
   move and the interim retire. A recommendation that has been discussed but not answered is still
   unapproved.
3. **Never implement an unapproved recommendation as though it were approved.** Until the owner
   answers, the Interim behavior column is the specification and the recommendation is a proposal
   about the future. Building the proposal early reintroduces exactly the silent choice rule 5 above
   calls a patient-safety-class bug.
4. **No recommendation states a clinical fact.** Where an answer requires a threshold, a normal range,
   a staleness cut-off, an alarm trigger, or a unit for a specific parameter, the recommendation names
   the mechanism and the owner — who supplies the value, in what shape, versioned against what, and
   what the UI does until it arrives — and never the value itself.

## How to read this file

| Column | Meaning |
|---|---|
| ID | Permanent. Never renumbered, never reused. `G-*` = data/handoff gap, `D-*` = design/visual, `P-*` = platform/engineering. |
| Question | The exact question to put to the owner. Written so it can be pasted into a ticket unchanged. |
| Why it blocks us | The concrete UI that cannot be rendered correctly, or the concrete wrong thing that would otherwise ship. |
| Owner | Who must answer: **backend**, **design**, **clinical**, **product**, **engineering**, **security**, **legal**, **IT**, or a combination joined with `+`. |
| Interim behavior | What the app does today while nobody has answered. Harness-defined, provisional, visible as such. It is not a proposal. |
| Recommendation `[PROPOSED]` | The answer we propose the owner adopt, specific enough to implement unchanged, naming the field, shape, endpoint, component, or policy, every file it lands in, and a cheaper `Fallback:` where one exists. It is **proposed, not decided** — approving it is the owner's act, and the Status column does not move until they do. It states no clinical value; where one is needed it names the mechanism and the owner instead. |
| Status | `OPEN-BLOCKING`, `OPEN`, `ANSWERED <date> — <answer>`, or `RETIRED <date> — <reason>`. |

`OPEN-BLOCKING` means that part of the UI is provisional at best and cannot be signed off as correct
until the answer lands.

## 4. Adding a row

1. Give it the next free ID in the right block. Never reuse a retired ID.
2. Write the Question so it can be pasted into a ticket without editing.
3. Write "Why it blocks us" as a concrete UI consequence, not an abstraction.
4. Name a single accountable Owner.
5. Describe the interim behavior exactly as implemented, and make sure the implementation carries the
   visible "harness-defined, pending design confirmation" label and a `data-clarify` id.
6. **Write a Recommendation. It is required, never `TBD`, and never a restatement of the interim.**
   Imperative and unhedged, in this fixed order: the proposed decision, the single strongest reason
   for it, a `Fallback:` clause where a cheaper option exists that we would also accept, and a
   closing `Lands in` clause. Two sentences of proposal is the target and five is the ceiling; the
   shape bounds the length, not a sentence count.
   Name the actual field, shape, value, endpoint, component, or policy, and name every file the
   answer lands in. Where the handoff already settles part of the question, say so and cite the
   section — a recommendation that contradicts the handoff is a defect.
7. **Hard constraint: never invent a clinical fact.** Do not propose a risk-score threshold, a
   staleness cut-off, a normal range, an alarm trigger, or a unit for a specific parameter. For those,
   recommend the mechanism and the owner instead — who supplies the value, in what shape, versioned
   against what, and what the UI does until it arrives. Proposing a value is a patient-safety-class
   error, not a style choice. Where a choice would make an unknown visible or make the screen look
   complete, recommend the one that makes the unknown visible.
8. Set the status, and mark it `OPEN-BLOCKING` if the affected UI cannot be signed off without the
   answer. Adding a recommendation never changes a Status.
9. **Tell the user you added it.**

## Gaps in the delivery itself, not in the design

Three files the harness depends on were not in the delivered copy. None is a design defect; all three
are recoverable.

1. **`.claude/` is absent.** `docs/` cites `patterns.md`, `bootstrap/SKILL.md`, the design-system and
   clinical-a11y skills roughly sixty times, and several modules name one of them as their canonical
   declaration. **`src/declaration-register.test.ts` reads
   `.claude/skills/bootstrap/SKILL.md` and therefore fails every one of its per-module assertions**
   against an empty string: 84 failures at delivery, before any change was made, and 89 now that five
   modules have been added. Every other test file passes. Supplying `.claude/` restores the gate.
2. **No `.gitignore`.** A `git add .` would have committed every dependency tree; `pnpm install` alone
   writes roughly 200 MB. One was added, and it keeps `.env` TRACKED on purpose: every key in it is a
   `PUBLIC_*` variable, compiled into the client bundle and public by definition.
3. **No `.prettierrc` or `.prettierignore`, so `pnpm lint` could not pass.** Without a config the
   svelte plugin never loads and every `.svelte` file errors with "No parser could be inferred", while
   `.ts` files are checked against prettier's defaults rather than the style the code is written in.
   A config was reconstructed **from the code itself, not guessed**: `singleQuote`, `printWidth: 100`,
   `endOfLine: auto` (the delivered files are CRLF), the svelte plugin, and `src/app.css` ignored
   because it is generated. The evidence that it is the right one is that all 113 pre-existing files
   pass under it unmodified. ⚠️ `prettier-plugin-tailwindcss` is a dependency but is NOT in the
   reconstructed config: with it enabled it reorders classes in 51 delivered files, so the code was
   not written with it active.
